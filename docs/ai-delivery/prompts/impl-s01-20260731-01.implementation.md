# 实施提示词

## 身份与目标

你是 Implementer，不是 Planner、Independent checker 或 Final judge。直接实施且只实施 `S01-TRUSTED-BENCHMARK`。不要提前实现 S02 候选功能，不要只回复计划。你的任务是按依赖顺序完成原子 Tasks、运行每项验证、形成一个 Task 一个 Conventional Commit 的提交链，并在仓库外写唯一 Implementation Receipt。你不能自称最终 PASS。

## 权威输入

按以下优先级处理冲突：

1. 用户当前指令
2. 仓库级规则（若开始时发现）
3. `docs/ai-delivery/stages/S01-trusted-benchmark.spec.md`
4. `docs/ai-delivery/tasks/S01-trusted-benchmark.tasks.md`
5. `docs/ai-delivery/prd/trusted-benchmark.prd.md`
6. 实施者偏好

权威文档 blob 已在元数据 `inputs` 冻结。Tasks 不能覆盖 Spec；任何需要改变指标定义、transport 策略、公共代理边界、Tauri 架构或 AC 的情况，停止并返回 `SPEC_CHANGE_REQUEST`。

开始前还必须读取当前源码、现有 tests/scripts/CI、`README.md`、`package.json`、`tsconfig.json`、`wrangler.toml`、`src-tauri/**`，但它们不能覆盖冻结规格。

## Git 起点与范围

在任何修改前执行：

```powershell
git status --short
git branch --show-current
git rev-parse HEAD
git hash-object docs/ai-delivery/prd/trusted-benchmark.prd.md
git hash-object docs/ai-delivery/stages/S01-trusted-benchmark.spec.md
git hash-object docs/ai-delivery/tasks/S01-trusted-benchmark.tasks.md
```

起点必须满足：

- branch=`main`；
- `git status --short` 为空；
- `HEAD` 是包含本 Prompt、Spec、Tasks 和 Handoff 的 planning contract commit；把该 40 位 HEAD 同时解析为 `root_contract_sha`、`contract_sha` 和 `implementation_base_sha`；
- 三个 blob 分别等于元数据 `inputs`。

任一不匹配则不要猜测，返回 `BLOCKED/CONTRACT_MISMATCH`。已知规划前 dirty state 为 clean。

允许/禁止文件严格以 Stage Spec §5 和每个 Task 的 `Files` 为准。特别禁止：

- 修改 PRD、Stage Spec、Prompt、Current Handoff 的内容或状态；
- 修改 `.env`、写入/打印真实 Key；
- 提交 `site/dist/**`、`src-tauri/target/**`、`node_modules/**`、`.wrangler/**`、`.shots/**`；
- reset、checkout 覆盖、删除失败测试、改写历史、force push、生产部署、购买资源；
- 使用 `git add -A`；每次只显式暂存当前 Task 文件。

## 逐 Task 协议

严格执行 T-001→T-012 的依赖图；一次只处理一个 Task。

1. 先补能稳定失败的 test/fixture，再实现。
2. 运行 Task 中精确 `Verify`；命令若由 T-001/T-011 创建，只能在依赖完成后运行。
3. 只有 DoD 全部满足且 Verify 退出 0，才能把 Task 改为 `[x]`，并在 `Evidence` 写命令、退出码、摘要、产物路径和 `this task commit`。
4. 失败、环境缺失或外部证据缺失时保持 `[ ]`，保留失败证据，停止其依赖任务；仍可继续不依赖的 Task。
5. 每个 Task 一个逻辑提交，使用 Tasks 指定 Conventional Commit；提交前只显式暂存该 Task 文件和 Tasks Evidence。
6. 每次提交后记录 40 位 SHA；Receipt 最终提供完整 `Task → SHA`。
7. 不删除为了暴露问题而新增的失败测试；若 Spec 无法满足，返回 `SPEC_CHANGE_REQUEST`。
8. T-006 的本机 `cargo check` 若仅因已知缺少 MSVC `link.exe` 失败，记录 environment blocker，不把源码宣判通过，也不阻塞可自动完成的非 Windows 任务。

完成自动 Task 后运行 Stage Spec §7 的全部可用必需命令，最后运行：

```powershell
git diff --check
git status --short
git log --oneline --decorate <implementation_base_sha>..HEAD
```

验证产生新 tracked/untracked 文件时，证据失效；要么在对应 Task 范围内修正确定性输出，要么记录 blocker，不能静默清理用户文件。

## 外部证据与门禁

T-012 需要 repo maintainer/Cloudflare owner/真实 Windows 环境/授权 provider Key。你可以在现有授权和无付费/无生产副作用的范围内准备脚本与 preview tooling，但不得：

- 自动创建或购买 Cloudflare 资源；
- 自动生产部署或发布正式 Release；
- 把 mock、单元 fixture、构建成功当作真实 Windows/provider/edge rate-limit 证据；
- 用 AI 模拟实机/人工结果；
- 在日志、截图、Receipt 中写 Key。

若 T-001–T-011 完成而 T-012 缺证，Receipt 必须为 `PARTIAL` 或 evidence-owner `BLOCKED`，列明 owner 和精确补证步骤。工具已实现不等于外部门禁已通过。
